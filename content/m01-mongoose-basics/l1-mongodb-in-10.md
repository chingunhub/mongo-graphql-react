We start at the bottom of the stack, because everything above it is shaped by how the data is stored. If you've used SQL before, some of this will feel like translation. If you haven't, even better — fewer habits to unlearn.

## Documents, not rows

MongoDB stores **documents**: JSON-looking objects. Here's a book from the little *Bookshelf* app we'll use for examples throughout Part I:

```json title="a document in the books collection"
{
  "_id": ObjectId("66f1c2a9e4b0a1b2c3d4e5f6"),
  "title": "The Left Hand of Darkness",
  "year": 1969,
  "tags": ["scifi", "classic"],
  "author": { "name": "Ursula K. Le Guin", "born": 1929 },
  "addedAt": ISODate("2024-03-02T10:15:00Z")
}
```

Three things to notice right away:

1. **Nesting is normal.** `author` is a whole object *inside* the book. `tags` is an array. In SQL you'd reach for extra tables; in Mongo, data that's read together can live together.
2. **It isn't really JSON — it's BSON.** "Binary JSON" has more types than JSON: real dates (`ISODate`), 32-bit vs 64-bit ints vs doubles, `Decimal128` for money, binary data, and `ObjectId`. When you see `"addedAt": "2024-03-02..."` as a string in a JSON response, that's the *API* serializing a real Date.
3. **Every document has an `_id`.** If you don't give one, the driver makes one for you.

Documents live in **collections**, collections live in **databases**:

Quick translation table if you're coming from SQL:

| SQL | MongoDB | Notes |
| --- | --- | --- |
| database | database | same idea |
| table | collection | but no enforced columns |
| row | document | can nest objects and arrays |
| column | field | can differ between documents |
| primary key | `_id` | always present, unique per collection |
| `JOIN` | embedding, `$lookup`, or Mongoose `populate` | Module 4 is all about this |

## "Schemaless" — and why that's a trap

MongoDB itself doesn't care what fields a document has. You can insert `{ title: "Dune" }` and `{ titel: "Dune", year: "nineteen sixty-five" }` into the same collection and it'll happily store both.

That flexibility is great for evolving data. It's terrible for bugs: a typo in a field name or a string where a number should be will sit in your database silently until something downstream breaks. **This is exactly the gap Mongoose fills**: it puts a schema in your *application* — types, required fields, validation, defaults — so the database only receives well-formed documents.

> [!IMPORTANT]
> The schema lives in your Node code, not in MongoDB. Anything that writes to the database *without* going through your Mongoose models (a script using the raw driver, a teammate in the shell, an old version of your app) can still write garbage. Keep that in mind when you're debugging "impossible" data in a big codebase.

## ObjectId: not just a random string

`_id` is usually an **ObjectId**, a 12-byte value. It's worth knowing what's inside, because it explains some behavior you'll see:

```viz objectid
```

Consequences that matter in practice:

- **It's generated by the client (the driver), not the database.** Mongoose knows a document's `_id` *before* it's saved. That's why `new Book({...})._id` already has a value.
- **The first 4 bytes are a timestamp**, so sorting by `_id` is *roughly* insertion order and `id.getTimestamp()` tells you when it was made. Roughly: ids from different machines in the same second can interleave. Don't build business logic on it; use a real `createdAt` field.
- **An ObjectId is not a string.** `{ _id: "66f1c2a9e4b0a1b2c3d4e5f6" }` in the raw driver matches *nothing*, because a string never equals an ObjectId. Mongoose saves you here by casting strings to ObjectIds based on your schema — but in a few places it can't (aggregation pipelines, Module 5), and that bug bites everyone once.
- **Not every string is a valid ObjectId.** It must be 24 hex characters. `findById("abc")` throws a `CastError` in Mongoose. Your API will receive bad ids from clients, so you'll handle this later.

## Querying: filters are documents too

A query is described by a **filter document** that looks like the documents you want:

```js
// exact match
db.books.find({ year: 1969 })

// operators start with $
db.books.find({ year: { $gte: 1960, $lt: 1970 } })

// reach into nested objects with "dot.notation" (quotes required)
db.books.find({ "author.name": "Ursula K. Le Guin" })

// arrays: matching a single value means "the array contains it"
db.books.find({ tags: "scifi" })
```

That last one surprises people: `{ tags: "scifi" }` matches `["scifi", "classic"]`. Mongo treats a scalar match against an array field as "any element equals". You'll use this constantly (labels on an issue, members of a project).

Here's how a filter flows through a query, conceptually:

```viz-pipeline
{
  title: 'db.books.find({ tags: "scifi", year: { $lt: 1970 } }).sort({ year: 1 })',
  input: {
    label: 'books',
    docs: [
      { title: 'Dune', year: 1965, tags: ['scifi'] },
      { title: 'Beloved', year: 1987, tags: ['literary'] },
      { title: 'Neuromancer', year: 1984, tags: ['scifi', 'cyberpunk'] },
      { title: 'The Left Hand of Darkness', year: 1969, tags: ['scifi', 'classic'] },
      { title: 'Foundation', year: 1951, tags: ['scifi'] },
    ],
    note: 'Five documents in the collection. MongoDB will keep the ones matching **every** condition in the filter.',
  },
  stages: [
    {
      label: 'filter',
      code: '{ tags: "scifi", year: { $lt: 1970 } }',
      docs: [
        { title: 'Dune', year: 1965, tags: ['scifi'] },
        { title: 'The Left Hand of Darkness', year: 1969, tags: ['scifi', 'classic'] },
        { title: 'Foundation', year: 1951, tags: ['scifi'] },
      ],
      note: '`Beloved` lacks the tag. `Neuromancer` has the tag but fails `$lt: 1970`. Conditions in one filter are ANDed.',
    },
    {
      label: 'sort',
      code: '{ year: 1 }',
      docs: [
        { title: 'Foundation', year: 1951, tags: ['scifi'] },
        { title: 'Dune', year: 1965, tags: ['scifi'] },
        { title: 'The Left Hand of Darkness', year: 1969, tags: ['scifi', 'classic'] },
      ],
      note: '`1` = ascending, `-1` = descending. Without a sort, MongoDB returns documents in whatever order is convenient for it — **never rely on that**.',
    },
  ],
}
```

## Indexes, in one paragraph (for now)

Without an index, MongoDB answers a query by scanning **every document** in the collection (a *collection scan*). With an index on `year`, it walks a sorted B-tree straight to the matching entries. On ten documents you can't tell the difference; on ten million it's milliseconds versus minutes. Every collection has an index on `_id` automatically. You'll declare more in Module 2 — including **unique** indexes, which are how "no two users with the same email" is actually enforced.

```quiz

- [x] `{ tags: "classic" }`
- [ ] `{ "tags.scifi": true }`
> Matching a single value against an array field means "the array contains this value". `{ tags: ["scifi"] }` would require the *whole array* to equal `["scifi"]` exactly.
```

```quiz

- [ ] The id is too long
- [x] The stored `_id` is an ObjectId, and a string never equals an ObjectId
- [ ] You must use `findOne` for ids
> BSON types are compared strictly. Mongoose casts strings to ObjectIds for you based on the schema, which hides this — until you're in code that skips the casting.
```

## What to take away

- Documents are BSON: nested, typed, each with an `_id`.
- MongoDB doesn't enforce structure. Mongoose enforces it **in your app**.
- ObjectIds are client-generated, timestamp-prefixed, and not strings.
- Filters are documents; dot notation reaches inside; scalar-vs-array matches "contains".
