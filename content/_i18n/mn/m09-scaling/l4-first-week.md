Чи дөнгөж жинхэнэ backend дуусгалаа, бүхэл бүтэн юм толгойд чинь багтдаг. Жинхэнэ repo багтахгүй.

Эхний өдөр ихэвчлэн ингэж өнгөрдөг. Clone хийхэд дөчин folder гарч ирнэ. Урьд нь сонсоогүй build tool ч бий. README-ийн setup гуравдугаар алхам дээрээ унана. Хэн нэгэн чамд хараахан юу ч хэлэхгүй үгсээр дүүрэн ticket өгнө. Чи өөрөөсөө чимээгүйхэн асууна: би хэзээ нэгэн цагт developer байсан юм болов уу?

Бараг хүн бүр үүнийг мэдэрдэг, олон хүн яг энд бууж өгдөг. Тэд repo өөрт нь "чи хангалттай сайн биш" гэж хэлж байна гэж боддог ч үнэндээ "чи шинэ" гэж л хэлж байгаа юм. Тийм хэмжээний repo-г хэн ч бүтнээр нь уншиж чадахгүй. Тэнд тайван харагддаг хүмүүс бүгдийг нь уншихгүйгээр ажиллах аргад л суралцсан хүмүүс.

Энэ хичээл яг үүний тухай. Дараа нь даалгавар байхгүй, учир нь ямар ч sandbox үүнийг дүгнэж чадахгүй. Хэрэг болсон өдөр нь эргэж ирээрэй.

## Юу өөрчлөгдөж, юу өөрчлөгддөггүй вэ

Taskforge-ийг том production repo-той зэрэгцүүлбэл ялгаа асар том харагдана:

| | Taskforge | Жинхэнэ repo |
| --- | --- | --- |
| Model-ууд | Цөөхөн | Олон зуу |
| Зохиолчид | Чи | Хэдэн арав, зарим нь хэдэн жилийн өмнө явсан |
| Чиний уншсан код | Бүгд | Тэнд ажиллах хугацаандаа жижиг хэсэг |
| Нэгдмэл байдал | Нэг хэв маяг | Өөр өөр жилийн хэд хэдэн хэв маяг |

Гэхдээ юу хэвээр байгааг хар. Client operation илгээдэг хэвээр. Schema юу зөвшөөрөгдсөнийг хэлдэг хэвээр. Resolver түүнийг хүлээн авч, хаа нэгтээ permission шалгаад, хаа нэгтээ database-тэй харилцана. Folder-уудын нэр өөр, тоо нь олон ч гэсэн request чиний гараар дөнгөж барьсан замаар л явдаг.

Layer бүрийг өөрөө бүтээсний жинхэнэ ашиг нь энэ. Чи юу хайхаа аль хэдийн мэднэ, тэгэхээр энэ repo үүнийг хаана хадгалдгийг олох л үлдэнэ.

## Эхний долоо хоногийн гурван зорилго

Энэ жагсаалтыг санаатайгаар богино байлга:

1. Өөрийн машин дээр **ажиллуул**.
2. **Нэг жижиг өөрчлөлтийг merge хийлгэ.** Үсгийн алдаа ч болно. README-ийн нэг мөр засах ч болно.
3. Юуны талаар **хэнээс асуухаа** ол.

Жагсаалтад юу байхгүйг анзаар: архитектурыг ойлгох. Үүнийг чи хэдэн сарын турш жинхэнэ өөрчлөлт хийж явахдаа олно. Урьдчилж судалъя гэж оролдсон ихэнх хүн долоо хоног уншаад юу ч санахгүй үлддэг.

Бүх service-ийн оронд ганцыг нь асааж болох бол тэгээрэй. Жижиг систем хурдан асдаг, error нь ч хавьгүй ойлгомжтой.

> Хязгаар тогтоо. Setup дээр нэг цаг орчим гацвал асуу. Дутуу environment variable-ийг таана гэж хэн ч хүлээдэггүй, хариулт нь ихэнхдээ зөвхөн багийнхны мэддэг зүйл байдаг.

## Нэг замыг дага

Энэ module-ийн эхэнд чи зан төлөвийг operation-аас data хүртэл мөрдөж сурсан. Том repo-г уншина гэдэг нь яг энэ. Үнэхээр тохиолддог нэг зүйлийг сонгоод, эхнээс нь дуустал дагаж, хажууд байгаа бусдыг орхино.

Жинхэнэ repo-д ижил зам илүү олон зогсоолтой: gateway, shared package, магадгүй өөр folder дахь service. Гэхдээ нэг удаад нэг алхам хийдэг нь өөрчлөгдөхгүй. Алхам бүрийг файл, function-ы нэртэй нь хамт бичиж яваарай. Эцэст нь өөрийн жижиг газрын зурагтай болно. Энэ нь хоёр жилийн өмнөх ямар ч архитектурын диаграммаас илүү үнэтэй.

Зам хаанаас эхэлдгийг олохын тулд яг таг зүйлийг хай:

- **Дэлгэц дээрх текст.** Товчны нэр эсвэл гарчиг кодод ихэвчлэн нэг-хоёр удаа гардаг.
- **Яг тэр error message.** Бүтнээр нь хуул. Энэ бол хаа нэгтээ файл дотор байгаа string.
- **Operation name**, browser-ийн network tab чамд үзүүлнэ.
- **Field-ийн нэр**, хаа хаагуур дамждагийг харахын тулд.

Дараа нь алхалтыг editor-оороо хийлгэ: **Go to definition** болон **Find all references**.

## Түүхээр кодыг тайлбарлуул

Буруу харагдах код олох нь элбэг, засахыг хүсэх нь амархан. Засахаасаа өмнө яагаад тэнд байгааг ол. Git санадаг:

```bash
# What changed in this file, newest first
git log --oneline -- server/services/permissions.ts

# Who last touched each line, and in which commit
git blame server/services/permissions.ts

# Which commits added or removed this string
git log -S"assertCanWriteProject" --oneline
```

Нэрнээс нь шалтгаалаад `git blame` хэн нэгнийг буруутгахад зориулагдсан мэт санагддаг ч тийм биш. Энэ чамайг commit руу, commit нь pull request руу хөтөлнө, тэр pull request сонин харагдах мөрийг ихэвчлэн тайлбарлаж өгдөг. Мөн тэр кодыг хэн мэддэгийг ч хэлдэг тул гурав дахь зорилгыг ч энэ шийднэ.

Саяхан merge болсон pull request-үүд бүр ч дээр. Чиний ticket-тэй төстэй зүйл хийсэн нэгийг олбол recipe гарт орно: ямар файл өөрчлөгдсөн, тест ямар байсан, reviewer-ууд юуг эсэргүүцсэн.

Тест ч адилхан тусална. Function-ы хажууд байгаа тест түүнийг хэрхэн дуудахыг, зохиолч юуг анхаарснаа харуулдаг, мөн ихэвчлэн кодоос нь уншихад хялбар. Ажиллаж байхдаа бүх suite-ийг биш, зөвхөн тэр нэг тестийг ажиллуул.

## Хамгийн ойрын хөршөөс хуул

Чиний эхний хэдэн даалгавар бараг бүгд repo-ийн өөр газар аль хэдийн хийгдэж байгаа зүйл байх болно. Тэгэхээр эхлээд тэр газрыг ол.

Taskforge-ийн issue дээр `estimate` field нэм гэсэн гэж бодъё. Юу ч зохиох шаардлагагүй. Нэг type дээр аль хэдийн байгаа `priority` field-ийг хай: гарсан үр дүн бүр чамд хөндөх хэрэгтэй байж болох газар. Нэг нэгээр нь тойроод үз, нэг мөр бичихээсээ өмнө өөрчлөлтийн жагсаалт чинь бэлэн болчихно.

Хэв маяг дээр ч адилхан. Өөрөөр хийх байсан ч өөрийн орсон файлынхаа хэв маягийг дага. Нэрлэлтийн талаар хатуу байр суурьтай шинэ хүн бүгдийг ядраадаг, харин кодоо эргэн тойрныхтойгоо адилхан бичдэг хүн review-ээр хурдан гардаг. Юм яагаад ингэж байгааг ойлгосны дараа, хэдэн сарын дараа өөрийн байр суурьтай болж болно.

> [!WARNING]
> Хуулж буй хөрш чинь хуучирсан биш эсэхийг шалга. Том repo-д хуучин арга, шинэ арга зэрэгцэж байх нь элбэг. Хуулж буй файлынхаа `git log`-ийг ажиллуул, аль нь одоогийнх вэ гэдэгт эргэлзэж байвал асуу.

## Сайн асуулт асуух

Хоёр өдөр чимээгүй гацах нь эрт асуухаас дор. Муу асуулт асуухаас ч дор, харин муу асуулт засахад амархан. Эхлээд жинхэнэ оролдлого хий, дараа нь дөрвөн зүйл бич:

```text
I'm trying to: add an estimate field to issues.
I expected: it to come back in the issue query.
What happened: "Cannot query field estimate on type Issue".
I've tried: adding it to the model and restarting.
My question: is the schema generated somewhere, or do I edit it by hand?
```

Үүнийг бичиж байхдаа хариултаа өөрөө олчих нь тал хувь нь. Үлдсэн тохиолдолд хэн нэгэн гучин секундэд хариулж чадах асуулт өгсөн болно. "Ажиллахгүй байна, нэг харчих уу?" гэвэл тэр хүнд хагас цаг зарцуулагдана.

## Чиний эхний pull request

Жижиг байлга. Нэг шалтгаанаар хийсэн нэг өөрчлөлтийг review хийхэд хавьгүй амар, тиймээс түргэн merge болдог. Ганцыг нь merge хийлгэхэд л бүх процесс сурагдана: branch-ийн нэр, check-үүд, энд review хэрхэн явдаг.

Review хүсэхээсээ өмнө өөрийнхөө diff-ийг өөр хүн бичсэн мэт уншаарай. Төөрсөн `console.log`-ийг ихэвчлэн барьчихна. Тест болон linter-ээ ажиллуулаад, юу өөрчлөгдсөн, яагаад, яаж шалгасанаа бич.

Дараа нь comment хүлээ. Хүн бүр авдаг, senior-ууд ч. Comment кодын тухай, чиний тухай биш. Тус бүр нь энэ repo-ийн талаар ямар ч курсын заадаггүй зүйлийг заана.

## Одоо чи хаана байна

Жинхэнэ repo руу орохоосоо өмнө энэ курсийг дуусгах шаардлагагүй. Чамд цээжилсэн баримтаас илүү зүйл бий: layer бүрийг өөрөө бүтээсэн тул тус бүр юунд зориулагдсаныг мэднэ. Үлдсэн нь цаг хугацаа, тэвчээр шаардана, хүн бүр үүгээр дамждаг.

Stage 3 руу үргэлжлүүлбэл Module 24 эдгээр зуршлаа ашиглан том open-source repo-г алхам алхмаар үзүүлнэ. Одоохондоо том repo чамайг төөрүүлэх бүрт санаарай: энэ бол чиний аль хэдийн барьсан зам, зүгээр л зогсоол нь олон.
